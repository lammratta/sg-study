## 要点

- システム化構想・計画では、経営目標に沿って**全体最適**の観点で対象業務を選び、投資対効果・スケジュール・体制と導入リスクを検討する
- 要件定義では、業務要件→機能要件・**非機能要件**（性能、可用性、セキュリティ）を定め、利害関係者の合意を得る。セキュリティ要件はこの段階で盛り込む
- 調達は**RFI**（情報提供依頼）→RFP（提案依頼）→提案評価→契約の順。RFPには対象範囲、要件、スケジュール、契約条件を明記する
- 提案評価は**評価基準と重み付け**を事前に決めて点数化し、費用だけでなく要求事項適合度、体制、実績で選定する
- 委託先には**情報セキュリティ要求事項**を提示し、選定基準（認証取得、管理体制、再委託の管理）で評価する

## 解説

### システム化構想と計画

**システム化構想**は、経営戦略と情報システム戦略に基づき、どの業務をどのようにシステム化するかの大枠を描く段階である。部門ごとの個別最適ではなく**全社の全体最適**を目指し、業務改革とセットで考える。

**システム化計画**では、次の事項を決めて経営層の承認を得る。

- 対象範囲
- 期待効果と投資額（投資対効果）
- 概略スケジュール
- 推進体制（経営層、利用部門、情報システム部門、ベンダーの役割）

### 情報システム導入リスク分析

計画段階では**情報システム導入リスク分析**も行う。リスク分析の対象を決め、リスクの発生頻度・影響・範囲を評価し、リスクの種類ごとに損害内容と損害額を見積もる（**リスク測定**）。

損失は次の4つに分けて考える。

| 損失の種類 | 内容 |
| --- | --- |
| 財産損失 | 設備やデータなどの財産が失われる |
| 責任損失 | 損害賠償などの責任を負う |
| 純収益損失 | 業務の停止によって収益が減る |
| 人的損失 | 従業員の死傷などによって人材を失う |

対応は次の5つから選び、リスク測定の結果に応じて優先順位を付ける。

| 対応 | 内容 |
| --- | --- |
| リスク回避 | 原因となる活動をやめ、リスクそのものをなくす |
| 損失予防 | 損失が発生する可能性を下げる |
| 損失軽減 | 発生したときの損失の大きさを小さくする |
| リスク移転 | 保険や契約によって損失を他者に移す |
| リスク保有 | 対策をとらず、損失を自ら負担する |

例題1: 障害によって年に平均2回、1回あたり150万円の損失が見込まれる業務に、年間200万円の対策を導入するかを判断する。年間の期待損失額は2×150＝300万円なので、対策費200万円の方が小さく、導入する方が合理的である。

**期待損失額＝発生頻度×損害額**が判断の基本になる。

### 要求分析と要件定義

**要求分析**は、利用者が何を求めているかを明らかにする作業で、ユーザーニーズ調査→調査内容の分析→現状分析→課題定義→**要求仕様書**の作成という手順で進める。要求項目を洗い出し、重要度や実現性で分析して優先順位を付ける。

**要件定義**は、要求を基にシステムが満たすべき条件を文書化する工程で、後工程の設計・開発・テストの基準になる。

- **業務要件定義**: システム化する業務の内容、業務処理手順、入出力、関係する組織
- **機能要件定義**: システムが実現すべき機能（画面、帳票、処理、データ）
- **非機能要件定義**: 性能、可用性、拡張性、運用・保守性、セキュリティなど機能以外の条件
- **セキュリティ要件**: アクセス制御、認証、暗号化、ログ取得、委託先の管理など
- **情報・データ要件**: 扱うデータの項目、量、保存期間、機密性

要件は、利用部門、情報システム部門、経営層などの**利害関係者の合意**を得て確定する。セキュリティ要件は後付けするとコストが大きくなるため、**この段階で盛り込む**。

### 調達計画と調達の実施

自社で開発・運用しきれない部分は外部資源を利用する。**システムインテグレータ**（SI事業者）は要件定義から構築・運用まで一括して請け負い、**アウトソーシング**は運用などの業務を外部に委託する。調達後は、ライセンス管理と構成管理によってシステム資産とソフトウェア資産を管理する。

調達の代表的な手順は次のとおり。

1. **RFI**（情報提供依頼書）: ベンダーに技術動向や製品情報、実績の提供を依頼し、実現方法の見通しを得る
2. **RFP**（提案依頼書）: 対象範囲、システムモデル、サービス要件、目標スケジュール、契約条件を示し、提案書と見積書の提出を求める。ベンダーの経営要件、プロジェクト体制要件、技術及び実績評価の観点も明記する。見積りだけを求める場合はRFQ（見積依頼書）を出す
3. **調達選定**: あらかじめ定めた提案評価基準（要求事項適合度、費用内訳、工程別スケジュール、最終納期、体制、実績）で提案を評価し、選定する
4. **契約締結**: 受け入れるシステムの内容、費用、受入時期、発注元とベンダーの役割分担を明確にする。契約書の雛形として、ソフトウェア開発委託モデル契約や、経済産業省が策定した情報システム・モデル取引・契約書がある。パッケージを利用するときは知的財産権利用許諾契約を結ぶ

例題2: 評価項目と重みを「機能適合度5、費用3、実績2」とし、各項目を5点満点で採点した結果がA社（4、3、5）、B社（5、2、3）、C社（3、5、4）だった。重み付き合計は、A社＝4×5＋3×3＋5×2＝39、B社＝5×5＋2×3＋3×2＝37、C社＝3×5＋5×3＋4×2＝38となり、A社を選定する。

費用の評価が最も高いC社が選ばれるとは限らない。**重みを事前に決めておくことで恣意的な選定を防ぐ**。

### 調達における情報セキュリティとグリーン調達

調達では、自社の情報セキュリティポリシーに基づく**情報セキュリティ要求事項**をRFPや契約に明示する。主な項目は次のとおり。

- 取り扱う情報の管理方法とアクセス制御
- 従業員の守秘義務
- 再委託の制限と事前承認
- インシデント発生時の報告義務
- 監査の受入れ
- 契約終了時のデータ返却・消去

**委託先選定基準**としては、ISMS認証（JIS Q 27001）やプライバシーマークの取得、情報セキュリティ管理体制、過去の事故歴、財務の健全性、技術力と実績を評価する。選定後も、定期的な報告や監査で**ベンダーの評価**を継続し、契約どおりに管理されているかを確認する。

**委託しても情報の管理責任は委託元に残る**点が重要である。

**グリーン調達**は、環境負荷の小さい製品やサービスを優先して購入することである。省電力の機器やリサイクルに配慮した製品の選定、グリーンITの推進が該当する。

## 試験での問われ方

- RFIとRFPの順序と目的（**情報収集が先、提案依頼が後**）を入れ替えた選択肢が出る
- 機能要件と非機能要件の区別。「応答時間3秒以内」「稼働率99.9%」「暗号化」は**非機能要件**
- 提案評価は「**あらかじめ定めた評価基準で点数化する**」が正答。価格だけで決める、評価中に基準を変えるのは誤り
- 委託契約に盛り込む情報セキュリティ要求事項（再委託の制限、インシデント報告、データ消去）と、**委託しても責任は委託元に残る**ことが問われる
- **期待損失額**（発生頻度×損害額）と対策費を比較してリスク対応を判断させる計算が出る
- 要件定義は利害関係者の合意が必要で、**情報システム部門だけで決めるのは誤り**

## 用語集

- **システム化構想**: 経営戦略と情報システム戦略に基づき、どの業務をどうシステム化するかの大枠を描くこと。
- **システム化計画**: 対象業務、投資対効果、スケジュール、体制を定め、経営層の承認を得る計画。
- **全体最適**: 部門ごとの最適ではなく、組織全体として最も効果が高くなるように考えること。
- **情報システム導入リスク分析**: 導入に伴うリスクの発生頻度・影響・範囲を評価し、損害額と対応を検討すること。
- **財産損失・責任損失・純収益損失・人的損失**: リスクによる損失の分類。設備の損失、賠償責任、業務停止による収益減、人への被害。
- **リスク回避・損失予防・損失軽減・リスク移転・リスク保有**: リスク対応の選択肢。原因除去、発生防止、影響縮小、保険等への転嫁、受容。
- **要求分析**: 利用者のニーズを調査・分析し、課題を定義して要求仕様書にまとめる作業。
- **要求仕様書**: 要求分析の結果として、システムに求める事項をまとめた文書。
- **要件定義**: システムが満たすべき業務要件・機能要件・非機能要件などを文書化し、利害関係者の合意を得る工程。
- **業務要件定義**: システム化する業務の内容や業務処理手順を定めること。
- **機能要件・非機能要件**: システムが実現すべき機能と、性能・可用性・セキュリティなど機能以外の条件。
- **セキュリティ要件**: 認証、アクセス制御、暗号化、ログなど、システムが備えるべき情報セキュリティの条件。
- **情報・データ要件**: 扱うデータの項目、量、保存期間、機密性などの条件。
- **システムインテグレータ（SI事業者）**: システムの企画から構築、運用までを一括して請け負う事業者。
- **アウトソーシング**: 業務やシステム運用を外部の専門事業者に委託すること。
- **ライセンス管理・構成管理**: ソフトウェアの利用許諾数とシステム資産の構成を記録・管理すること。
- **RFI**: 情報提供依頼書。ベンダーに技術や製品の情報、実績の提供を求める文書。
- **RFP**: 提案依頼書。調達の対象範囲や要件、スケジュール、契約条件を示し、提案を求める文書。
- **RFQ**: 見積依頼書。提案ではなく見積りの提出を求める文書。
- **提案評価基準**: 要求事項適合度、費用内訳、工程別スケジュール、最終納期、体制、実績など提案を評価する基準。
- **提案書・見積書**: ベンダーがRFPに応じて提出する、実現方法と費用を示した文書。
- **ソフトウェア開発委託モデル契約・情報システム・モデル取引・契約書**: 発注元とベンダーの役割分担や責任を定めた契約書の雛形。
- **知的財産権利用許諾契約**: ソフトウェアなどの知的財産を利用する条件を定めた契約。
- **グリーン調達**: 環境負荷の小さい製品やサービスを優先して調達すること。
- **情報セキュリティ要求事項の提示**: 委託先に求める情報の管理方法、再委託の制限、インシデント報告などをRFPや契約で明示すること。
- **委託先選定基準**: ISMS認証やプライバシーマークの取得、管理体制、実績、財務の健全性などで委託先を評価する基準。
- **ベンダーの評価**: 選定時と契約期間中に、技術力、実績、体制、セキュリティ管理状況を継続的に評価すること。
