## 要点

- **共通鍵暗号**（AESなど）は暗号化と復号に同じ鍵を使い、高速だが鍵の安全な配送が課題。n人の相互通信にはn(n-1)/2個の鍵が要る
- **公開鍵暗号**（RSA、楕円曲線暗号）は公開鍵で暗号化し、対になる秘密鍵でだけ復号できる。鍵配送の問題を解決するが処理が遅い
- **ハイブリッド暗号**は、データ本体を共通鍵で暗号化し、その共通鍵を受信者の公開鍵で暗号化して送る。共通鍵（セッション鍵）は通信ごとに作り直す。TLSやS/MIMEで使われる
- **ハッシュ関数**（SHA-256など）は任意長のデータから固定長のハッシュ値を作り、元に戻せず、同じハッシュ値をもつ別データを作ることが困難。改ざん検知とパスワード保存に使う
- **デジタル署名**は送信者の秘密鍵で署名し、公開鍵で検証する。完全性・真正性・否認防止を確保。公開鍵が本人のものである保証を与えるのがPKIとデジタル証明書で、証明書の正当性は認証局（CA）の公開鍵で署名を検証して確かめる
- 暗号の**危殆化**（コンピュータの高速化や攻撃法の発見で安全でなくなること）に備え、CRYPTREC暗号リストの推奨アルゴリズムを使い、鍵長とアルゴリズムを見直す

## 解説

### 暗号の基本と共通鍵暗号方式

**暗号化**とは、平文を鍵を使って第三者に読めない暗号文に変換することで、暗号文を平文に戻すことを**復号**という。暗号化に使う鍵が暗号鍵、復号に使う鍵が復号鍵である。

**共通鍵暗号方式**は、暗号化と復号に同じ鍵（共通鍵）を使う。代表は米国NISTが標準化した**AES**（鍵長128・192・256ビット）である。処理が高速で大量のデータの暗号化に向くが、通信相手ごとに別の鍵が必要で、相手に鍵を安全に渡す「鍵配送問題」がある。

n人が相互に通信するには、n(n-1)/2個の鍵が必要になる。共通鍵暗号の安全性は鍵を秘密に保つことと十分な鍵長に支えられており、**素因数分解の難しさを根拠とするのはRSA暗号（公開鍵暗号）であって、共通鍵暗号ではない**。

暗号化の単位によって、一定長のブロックごとに暗号化する**ブロック暗号**（AESなど）と、ビットやバイト単位で逐次暗号化する**ストリーム暗号**に分かれる。

### 公開鍵暗号方式

**公開鍵暗号方式**は、対になる2つの鍵のうち一方を**公開鍵**として誰にでも配り、もう一方を**秘密鍵**として本人だけが保管する。公開鍵で暗号化した暗号文は、対応する秘密鍵でしか復号できない。

そこで、**送信者は受信者の公開鍵で暗号化し、受信者は自分の秘密鍵で復号する**。鍵の配送は不要になるが、処理が遅いのが欠点である。

| 方式 | 安全性の根拠 | 特徴 |
| --- | --- | --- |
| RSA暗号 | 大きな数の素因数分解が難しいこと | 暗号化と署名の両方に使える |
| 楕円曲線暗号（ECC） | 楕円曲線上の離散対数問題が難しいこと | RSAより短い鍵長で同等の強度 |

### ハイブリッド暗号とセッション鍵

実際の通信では、両者を組み合わせた**ハイブリッド暗号**が使われる。データ本体は高速な共通鍵暗号で暗号化し、その共通鍵を受信者の公開鍵で暗号化して一緒に送る。受信者は自分の秘密鍵で共通鍵を取り出し、データ本体を復号する。

**公開鍵で暗号化するのはデータ本体ではなく共通鍵である**。鍵管理の手間と処理性能を両立でき、TLSや、電子メールを暗号化するS/MIME、OpenPGPで使われる。

この共通鍵を**セッション鍵**といい、通信（セッション）のたびに作って使い捨てる。一方、証明書に載せる公開鍵と秘密鍵の対は、証明書の有効期間中は使い続ける。**通信ごとに作り直すのは共通鍵の側**である。

### ハッシュ関数とソルト

**ハッシュ関数**は、任意の長さのデータから固定長のハッシュ値（メッセージダイジェスト）を計算する関数で、代表はSHA-2（SHA-256など）とSHA-3である。

- **一方向性**: ハッシュ値から元のデータを復元できない。復号できないので、暗号化には使えない
- **衝突困難性**: 同じハッシュ値になる別のデータを見つけることが困難である
- **固定長**: 入力の長さによらず出力の長さは一定。SHA-256は常に256ビット（32バイト、16進数で64桁。16進数1桁は4ビット）

同じ入力からは常に同じハッシュ値になり、入力が少しでも違えば全く異なる値になる。そのため、**ハッシュ値が一致すれば内容は同じとみなせ**、ファイルの改ざんの確認に使える。

パスワードはハッシュ値で保存するが、同じパスワードは同じハッシュ値になるため、レインボーテーブル攻撃で逆引きされる。そこで利用者ごとに異なるランダムな値（**ソルト**）を付加してからハッシュ化し、対応表による逆引きを無効化する。

### デジタル署名とメッセージ認証符号

**デジタル署名**は、公開鍵暗号の鍵を暗号化とは逆向きに使う。送信者はデータのハッシュ値を自分の秘密鍵（署名鍵）で処理して署名を作り、データと一緒に送る。受信者は送信者の公開鍵（検証鍵）で署名からハッシュ値を取り出し、受け取ったデータから計算したハッシュ値と比較する。

一致すれば、改ざんされていない（完全性）、秘密鍵の持ち主が署名した（真正性）ことが確認でき、秘密鍵は本人しか持たないため後から否定できない（否認防止）。**デジタル署名は機密性を守るものではない**。

| 目的 | 使う鍵 |
| --- | --- |
| 暗号化 | 受信者の公開鍵 |
| 復号 | 受信者の秘密鍵 |
| 署名の作成 | 送信者の秘密鍵 |
| 署名の検証 | 送信者の公開鍵 |

**メッセージ認証符号**（MAC）は、送受信者が共有する共通鍵とメッセージから計算する符号で、受信者が同じ鍵で再計算して一致を確認する。ハッシュ関数を使う方式（HMAC）のほか、**ブロック暗号を使う方式**（AESを使うCMACなど）でも作れる。

MACで改ざんの有無は確認できるが、**鍵を両者が持つため、どちらが作ったかを第三者に証明できず、否認防止はできない**。

**パリティビット**は、データ中の1の個数が偶数（又は奇数）になるように付ける1ビットで、伝送中の偶然の誤りを検出するためのものである。鍵を使わず誰でも付け直せるので、**意図的な改ざんの検知には使えない**。

### PKIとデジタル証明書

公開鍵が本人のものである保証がなければ、なりすましが可能になる。**PKI**（公開鍵基盤）はこれを解決する仕組みで、信頼できる第三者である**認証局**（CA）が審査のうえ、公開鍵と所有者情報にCAのデジタル署名を付けた**デジタル証明書**（公開鍵証明書）を発行する。Webサーバ用のサーバ証明書、利用者や端末用のクライアント証明書などがある。

頂点にあるルートCAの自己署名証明書が**ルート証明書**で、信頼の基点（トラストアンカー）としてOSやブラウザに組み込まれている。「ルート証明書→中間CA証明書→サーバ証明書」という証明書チェーンをたどり、上位の証明書の公開鍵で下位の証明書の署名を検証する。

サーバ証明書は、CAによる審査の厳しさで分かれる。

| 種類 | CAが確認すること |
| --- | --- |
| DV証明書 | ドメイン名の利用権だけ |
| OV証明書 | ドメイン名の利用権と、組織の実在 |
| EV証明書 | 最も厳格な審査で、ドメイン名の利用権と、組織の法的・物理的な実在性 |

### 証明書の失効とタイムスタンプ

有効期限内でも、秘密鍵の漏えいなどで証明書を無効にする（失効させる）ことがある。CAは失効した証明書を**CRL**（証明書失効リスト）に載せて公開する。個別の証明書の有効性をリアルタイムに問い合わせるプロトコルが**OCSP**である。

**CRLは失効した証明書の一覧であり、有効期限切れの一覧ではない**。

**タイムスタンプ**（時刻認証）は、時刻認証局が信頼できる時刻を付けて署名し、その時刻にデータが存在し以後改ざんされていないことを証明する。

### サーバ証明書の検証と鍵の役割

Webサイトとの暗号化通信（TLS、詳しくはセキュアプロトコルのページ）では、ブラウザはサーバ証明書を受け取ると、まず**証明書に付いたCAの署名を、CAの公開鍵で検証する**。CAの公開鍵は上位の証明書に入っており、たどるとブラウザやOSが持つルート証明書に行き着く。あわせて有効期限、接続先のドメイン名との一致、失効していないか（CRL、OCSP）を確かめる。

検証できれば、証明書は改ざんされておらず、信頼できるCAが発行した正当なものとわかる。検証に失敗すると、ブラウザは警告を表示する。証明書に入っているサーバの公開鍵は、通信用の共通鍵（セッション鍵）を安全に共有するために使う。

| 鍵 | 持っている者 | 使い道 |
| --- | --- | --- |
| CAの秘密鍵 | 認証局 | 証明書に署名する |
| CAの公開鍵 | ブラウザ・OS（ルート証明書など） | 証明書の署名を検証する |
| サーバの公開鍵 | 誰でも（サーバ証明書に入っている） | 共通鍵を安全に共有する（共通鍵を暗号化して送るなど） |
| サーバの秘密鍵 | サーバ | 共通鍵の共有で使う（暗号化された共通鍵の復号など） |
| 共通鍵（セッション鍵） | ブラウザとサーバ | 通信データを暗号化・復号する |

**CAの公開鍵の役割は証明書の署名の検証であり、共通鍵の暗号化・復号や送信データの暗号化には使わない**。

### 鍵管理・危殆化・CRYPTREC

**鍵管理**では、鍵の生成、配布、保管、更新、廃棄の各段階で権限のない者に触れさせず、有効期間を定めて更新し、暗号化データと鍵を同じ場所に置かない。

暗号の**危殆化**とは、コンピュータの性能向上や新しい解読手法の発見によって、安全とされていたアルゴリズムや鍵長が安全でなくなることで、MD5やSHA-1が該当する。アルゴリズムと鍵長を定期的に見直すことが対策である。

CRYPTRECは総務省と経済産業省が共同運営する暗号技術の評価プロジェクトで、**CRYPTREC暗号リスト**は電子政府推奨暗号リストなど3つのリストから成り、政府機関の調達で使う暗号の基準になっている。暗号は公開され評価を受けた標準的な方式を使い、**独自に作った暗号は安全性を確かめられないので避ける**。

### ストレージ暗号化とファイル暗号化

| 方式 | 暗号化する範囲 | 主な用途と注意 |
| --- | --- | --- |
| ストレージ暗号化 | ディスク全体 | ノートPCやUSBメモリの紛失・盗難時にデータを読み取られないようにする。**ログイン中は復号される**ため、マルウェアや盗み見には効果がない |
| ファイル暗号化 | 個々のファイル | 持出しやメール添付のときに、そのファイルを保護する |

## 試験での問われ方

- 「**どの鍵を何に使うか**」が最頻出。暗号化＝受信者の公開鍵、復号＝受信者の秘密鍵、署名＝送信者の秘密鍵、検証＝送信者の公開鍵。TLSで認証局の公開鍵を使うのはサーバ証明書の署名の検証で、共通鍵の受渡しにはサーバの公開鍵を使う
- 共通鍵暗号と公開鍵暗号の比較: 共通鍵は**高速だが鍵配送が課題**、公開鍵は鍵配送が不要だが低速。大量データの暗号化には共通鍵が向く。鍵の個数の計算（n(n-1)/2）も出る。素因数分解の困難さが根拠なのはRSAで、共通鍵暗号ではない
- ハイブリッド暗号で「公開鍵で暗号化するのは**共通鍵**」である点。共通鍵（セッション鍵）は通信ごとに作り直し、公開鍵と秘密鍵の対は長く使う
- ハッシュ関数の性質（元に戻せない、**固定長**、衝突困難、同じ入力なら同じ値）。SHA-256は256ビット＝32バイト＝16進数64桁。ハッシュ関数は暗号化（復号できる変換）ではない。ソルトの目的はレインボーテーブル対策
- デジタル署名が保証するのは完全性・真正性・否認防止で、**機密性ではない**。MACは否認防止ができず、ハッシュ関数やブロック暗号で作れる。パリティビットは改ざん検知に使えない
- CRLは失効した証明書の一覧であり、**有効期限切れの一覧ではない**。ルート証明書は信頼の基点。危殆化は「暗号の安全性が時間とともに低下すること」

## 用語集

- **暗号化・復号**: 平文を暗号文に変換することが暗号化、暗号文を平文に戻すことが復号。それぞれ暗号鍵、復号鍵を使う
- **共通鍵暗号方式**: 暗号化と復号に同じ鍵を使う方式。高速だが鍵配送問題がある
- **公開鍵暗号方式**: 公開鍵と秘密鍵の対を使う方式。公開鍵で暗号化し秘密鍵で復号する。鍵配送が不要
- **AES**: 米国NISTが標準化した共通鍵暗号のアルゴリズム。鍵長128・192・256ビットのブロック暗号
- **RSA暗号**: 大きな数の素因数分解の困難さを利用した公開鍵暗号。暗号化と署名の両方に使える
- **楕円曲線暗号（ECC）**: 楕円曲線上の演算を利用した公開鍵暗号。RSAより短い鍵長で同等の強度
- **ブロック暗号・ストリーム暗号**: 一定長のブロック単位で暗号化するのがブロック暗号、ビット・バイト単位で逐次暗号化するのがストリーム暗号
- **ハイブリッド暗号**: データを共通鍵で暗号化し、その共通鍵を公開鍵で暗号化して送る方式。TLSなどで利用
- **セッション鍵**: 通信（セッション）ごとに生成して使い捨てる共通鍵。ハイブリッド暗号でデータ本体の暗号化に使う
- **ハッシュ関数**: 任意長のデータから固定長のハッシュ値を計算する一方向性の関数。同じ入力からは常に同じ値になる。SHA-256が代表
- **メッセージダイジェスト**: ハッシュ関数で計算したハッシュ値。改ざん検知に使う
- **SHA-2・SHA-3**: 現在推奨されるハッシュ関数の規格。SHA-256はSHA-2の一種で、出力は256ビット。MD5とSHA-1は危殆化
- **ソルト**: パスワードのハッシュ化時に付加するランダムな値。レインボーテーブル攻撃を無効化する
- **デジタル署名**: 送信者の秘密鍵（署名鍵）で署名し、公開鍵（検証鍵）で検証する仕組み。完全性・真正性・否認防止を確保
- **メッセージ認証符号（MAC）**: 共通鍵とメッセージから計算する符号。ハッシュ関数やブロック暗号で作る。改ざん検知と送信元確認（メッセージ認証）ができるが否認防止はできない
- **PKI（公開鍵基盤）**: 認証局とデジタル証明書によって公開鍵の正当性を保証する仕組み
- **認証局（CA）**: 本人確認のうえでデジタル証明書を発行し、失効を管理する機関
- **デジタル証明書（公開鍵証明書）**: 公開鍵と所有者情報にCAが署名したもの。正当性はCAの公開鍵で署名を検証して確かめる
- **サーバ証明書・クライアント証明書**: サーバ証明書はWebサーバなどの公開鍵とドメイン名を、クライアント証明書は利用者や端末を証明するデジタル証明書。サーバ証明書は審査の厳しさでDV・OV・EVに分かれる
- **ルート証明書**: ルートCAの自己署名証明書。信頼の基点（トラストアンカー）としてブラウザなどに組み込まれる
- **中間CA証明書**: ルートCAの下位にある中間CAの証明書。証明書チェーンを構成する
- **CRL（証明書失効リスト）**: 有効期限内に失効した証明書の一覧。CAが公開する
- **OCSP**: 証明書の失効状態をリアルタイムに問い合わせるプロトコル。CRLの代替
- **タイムスタンプ（時刻認証）**: 時刻認証局がデータの存在時刻と非改ざんを証明する仕組み
- **鍵管理**: 鍵の生成・配布・保管・更新・廃棄を安全に行うこと。暗号の安全性の前提
- **危殆化**: 計算能力の向上や攻撃法の発見で暗号の安全性が低下すること。アルゴリズムと鍵長の見直しで対処
- **CRYPTREC暗号リスト**: 総務省と経済産業省が運営するCRYPTRECが公開する、安全性を評価した暗号技術のリスト
- **ストレージ暗号化**: ディスク全体を暗号化し、紛失・盗難時のデータ読取りを防ぐ。BitLockerなど
- **ファイル暗号化**: 個々のファイルを暗号化して保護すること。持出しやメール添付時に使う
